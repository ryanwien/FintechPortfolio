Same order types, same priority and self-trade rules, same synthetic flow shape; flows are not command-for-command identical because the two languages use different RNGs.

## Methodology and variance

- Throughput is a tight untimed-per-op loop over the whole flow on a fresh engine, best of 3 runs; the slower runs are scheduler and cache noise on a shared laptop. This run's three rates are in the table above; expect roughly +-20% between runs.
- Latency is a separate pass that brackets each `process()` call with `steady_clock::now()`, the same per-op method the Python bench uses. On Windows that clock ticks in 100 ns steps and the timer call itself costs tens of nanoseconds, so sub-microsecond percentiles are quantized and biased upward; the throughput number, which has no per-op timer, is the fairer speed figure.
- Depth is sampled every 1,000 commands.
- Determinism: the identical command log fed to a fresh engine reproduces the FNV-1a book hash (`02dfcc0117b1d90a`). The flow generator itself is deterministic per seed and platform; its mid path uses libm, so bit-identical flows across different C runtimes are not guaranteed.
- The comparison with Python is throughput ratio on the same machine and the same flow shape, not a command-for-command race: the Python benchmark ran 300,000 commands with its own RNG, this one runs 1,000,000 with splitmix64. Both books hold a similar number of levels and resting orders at steady state.
